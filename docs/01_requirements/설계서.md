# 통합 서버 모니터링 관제 시스템 요구사항 및 구현 분리 설계서

- 문서 버전: 1.0
- 대상 데이터베이스: Oracle Database
- 대상 서버 운영체제: Windows Server, Linux
- 구성 방식: 서버별 수집 데몬(Agent) + 중앙 API 서버 + Oracle DB + Web 관제 화면
- 문서 목적: 기능 요구사항을 기능 단위로 세분화하고, 각 요구사항의 구현 책임을 DB·API·데몬·웹 화면으로 구분한다.

---

# 1. 시스템 개요

## 1.1 구축 목적

본 시스템은 여러 서버, 애플리케이션, 데이터베이스, 배치, 파일 연계, 네트워크 장비 및 업무 처리 상태를 하나의 관제 사이트에서 통합 감시하기 위한 시스템이다.

각 대상 서버에는 경량 데몬을 설치하고, 데몬이 서버 자원 및 업무 상태를 수집하여 중앙 API 서버로 전송한다. API 서버는 데이터를 검증·저장·집계하고, 이벤트 및 장애를 판정하여 Oracle DB에 기록한다. Web 화면은 Oracle DB에 저장된 현재 상태, 이력, 이벤트, 장애, 통계 및 설정 정보를 API를 통해 조회한다.

## 1.2 구축 원칙

1. 서버 운영체제별 수집 방식은 Windows와 Linux로 분리한다.
2. 서버별 모니터링 항목은 설정으로 활성화·비활성화할 수 있어야 한다.
3. 서버별 임계치, 수집 주기, 보관 주기를 개별 설정할 수 있어야 한다.
4. 수집 데몬은 중앙 서버 장애 또는 네트워크 단절 시 로컬에 임시 저장한 후 재전송할 수 있어야 한다.
5. 현재 상태와 장기 이력 데이터를 분리하여 저장한다.
6. 이벤트 발생, 알림 전송, 장애 접수, 조치, 복구, 종료의 전체 이력을 관리한다.
7. 관제 Web에서 수행한 설정 변경 및 원격 명령은 모두 감사 로그로 남겨야 한다.
8. 중앙 저장소는 Oracle Database를 사용한다.
9. 대량 시계열 데이터는 파티션, 집계 테이블, 보관 정책을 적용한다.
10. API 서버와 수집 데몬 간 통신은 TLS 기반으로 보호한다.

## 1.3 구성 요소

| 구성 요소 | 역할 |
|---|---|
| 대상 서버 | Windows 또는 Linux 기반 WEB, WAS, DB, 분석, 배치, 파일 연계 서버 |
| 수집 데몬 | 서버 자원, 프로세스, 서비스, 로그 및 업무 상태 수집 |
| 중앙 API 서버 | 데몬 등록, 데이터 수신, 상태 조회, 설정 관리, 이벤트 처리 |
| 이벤트 처리기 | 임계치 판정, 이벤트 생성·해제, 중복 억제, 장애 연계 |
| 알림 처리기 | 이메일, SMS, 메신저 등 알림 채널 전송 |
| Oracle DB | 설정, 현재 상태, 이력, 이벤트, 장애, 사용자, 감사 로그 저장 |
| Web 관제 화면 | 대시보드, 서버 상세, 이벤트, 장애, 로그, 통계, 설정 화면 |
| 스케줄러 | 집계, 보관기간 정리, 보고서 생성, 미수신 서버 판정 |
| 관리자 | 서버 등록, 임계치 설정, 사용자 및 권한 관리 |
| 관제 사용자 | 상태 조회, 이벤트 확인, 장애 조치 및 보고서 조회 |

## 1.4 기본 데이터 흐름

```text
[Windows/Linux 대상 서버]
        │
        │ 서버별 수집 데몬
        │ - 자원 수집
        │ - 프로세스/서비스 수집
        │ - 로그 수집
        │ - 업무 상태 수집
        ▼
[중앙 API 서버]
        │
        ├─ 인증 및 데이터 검증
        ├─ 현재 상태 갱신
        ├─ 이력 데이터 저장
        ├─ 임계치 및 이벤트 판정
        ├─ 장애 및 알림 처리
        ▼
[Oracle Database]
        ▲
        │ 조회·설정·명령 API
        │
[Web 통합 관제 화면]
```

# 3. 전체 아키텍처 요구사항

## 3.1 중앙 집중형 구성

### MON-ARC-001 중앙 API 서버 구성

- 모든 수집 데몬은 중앙 API 서버를 통해 데이터를 등록한다.
- 데몬이 Oracle DB에 직접 접속하지 않도록 한다.
- API 서버는 데이터 검증, 인증, 저장 및 조회를 담당한다.
- API 서버는 수평 확장이 가능하도록 무상태 구조를 권장한다.

**DB 구현**
- API 인스턴스 정보, 처리 이력, 실패 이력을 선택적으로 저장한다.
- 데이터 저장 트랜잭션과 이벤트 생성 트랜잭션의 경계를 정의한다.

**API 구현**
- Agent용 API와 Web용 API를 논리적으로 분리한다.
- `/agent/v1/*`, `/api/v1/*`, `/admin/v1/*` 형식으로 구분한다.
- 서버 식별자, 에이전트 식별자, 전송 순번, 수집시각을 검증한다.

**데몬 구현**
- 중앙 API 주소를 설정 파일에서 관리한다.
- 여러 API 주소를 설정할 수 있도록 하여 장애 시 보조 주소로 전환할 수 있게 한다.
- API 접속 실패 시 로컬 스풀에 저장하고 재전송한다.

**웹 화면 구현**
- 중앙 API 상태와 마지막 데이터 처리 시각을 운영 화면에서 확인할 수 있게 한다.

### MON-ARC-002 데이터 처리 구분

데이터는 다음 네 종류로 구분한다.

1. 기준 및 설정 데이터
2. 현재 상태 데이터
3. 원시 이력 데이터
4. 집계 데이터

**DB 구현**
- 현재 상태 테이블은 서버·항목별 최신 1건을 유지한다.
- 이력 테이블은 수집 주기에 따라 지속 적재한다.
- 집계 테이블은 5분, 1시간, 1일 단위로 분리한다.
- 대용량 이력 테이블은 수집일시 기준 파티션을 적용한다.

**API 구현**
- 현재 상태 조회 API와 기간 이력 조회 API를 분리한다.
- 대량 이력 조회는 페이지네이션 또는 시간 구간 제한을 적용한다.

**데몬 구현**
- 수집시각과 전송시각을 구분하여 전송한다.
- 데이터 항목별 단위와 품질 상태를 포함한다.

**웹 화면 구현**
- 현재값, 평균값, 최대값, 추세값을 구분하여 표시한다.

### MON-ARC-003 Windows/Linux 공통 모델

- 동일한 논리 지표는 OS가 달라도 동일한 지표 코드로 저장한다.
- OS별 수집 방법은 데몬 내부 Collector 구현으로 분리한다.
- OS에서 제공하지 않는 지표는 `UNSUPPORTED` 상태로 처리한다.

# 4. 서버 및 에이전트 관리

## 4.1 서버 기본정보 관리

### MON-SRV-001 서버 등록

서버별로 다음 정보를 등록한다.

- 서버 ID
- 서버명
- 호스트명
- 관리 IP
- 서비스 IP
- 운영체제 유형
- 운영체제 버전
- 서버 역할
- 운영·개발·검증 환경 구분
- 물리·가상·클라우드 구분
- 설치 위치
- 담당 부서
- 담당자
- 중요도
- 사용 여부
- 등록일시
- 최종 수정일시

**DB 구현**
- `MON_SERVER` 테이블에 저장한다.
- 서버명, 호스트명, 관리 IP에 검색 인덱스를 생성한다.
- 서버 삭제는 물리 삭제보다 사용 여부 변경을 기본으로 한다.

**API 구현**
- 서버 등록, 수정, 상세 조회, 목록 조회, 사용 중지 API를 제공한다.
- IP 중복, 서버명 중복 정책을 검증한다.
- 서버 역할 및 운영환경 코드는 공통코드로 관리한다.

**데몬 구현**
- 최초 등록 시 호스트명, OS, IP, 에이전트 버전을 자동 전송한다.
- 중앙에서 승인되기 전까지 데이터 전송을 제한할 수 있다.

**웹 화면 구현**
- 서버 목록, 등록, 수정, 상세 화면을 제공한다.
- 서버 역할, 환경, OS, 상태, 담당자 기준 필터를 제공한다.

## 4.2 서버 그룹 및 태그

### MON-SRV-002 서버 그룹 관리

- 시스템별, 업무별, 망별, 센터별, 환경별 서버 그룹을 구성한다.
- 하나의 서버가 여러 그룹에 포함될 수 있어야 한다.

**DB 구현**
- `MON_SERVER_GROUP`
- `MON_SERVER_GROUP_MAP`

**API 구현**
- 그룹 CRUD 및 서버 배정 API를 제공한다.

**데몬 구현**
- 구현 대상 없음. 중앙 설정 수신 시 그룹 기반 정책을 적용할 수 있다.

**웹 화면 구현**
- 트리형 그룹 관리 및 드래그 배정 기능을 제공할 수 있다.
- 그룹별 상태 요약을 표시한다.

### MON-SRV-003 서버 태그 관리

- `WEB`, `WAS`, `DB`, `BATCH`, `ACTIVE`, `STANDBY` 등 임의 태그를 부여한다.

**DB 구현**
- `MON_TAG`
- `MON_SERVER_TAG`

**API 구현**
- 태그 등록, 삭제, 서버 태그 연결 API를 제공한다.

**데몬 구현**
- 중앙 설정에 따라 태그별 Collector를 활성화할 수 있다.

**웹 화면 구현**
- 태그 검색과 태그별 대시보드 필터를 제공한다.

## 4.3 에이전트 등록 및 인증

### MON-SRV-004 에이전트 등록

에이전트는 다음 정보를 관리한다.

- Agent ID
- 서버 ID
- Agent 버전
- 설치 경로
- 실행 계정
- 시작 시각
- 최종 접속 시각
- 최종 설정 반영 버전
- 상태
- 인증서 또는 토큰 식별자
- 자동 업데이트 가능 여부

**DB 구현**
- `MON_AGENT`
- `MON_AGENT_AUTH`
- `MON_AGENT_VERSION`

**API 구현**
- 에이전트 등록 요청, 승인, 인증정보 발급, 폐기 API를 제공한다.
- 재설치 시 기존 Agent ID 재사용 또는 신규 발급 정책을 지원한다.

**데몬 구현**
- 최초 실행 시 서버 지문을 생성한다.
- 등록 토큰 또는 인증서를 이용하여 중앙에 등록한다.
- 인증정보는 평문 설정 파일에 저장하지 않는다.

**웹 화면 구현**
- 미승인 에이전트 목록, 승인, 차단, 인증 폐기 기능을 제공한다.

### MON-SRV-005 하트비트 수집

- 기본 주기는 30초에서 60초 사이로 설정 가능해야 한다.
- 마지막 하트비트 지연시간으로 정상, 지연, 미수신 상태를 판단한다.

**DB 구현**
- `MON_AGENT_STATUS_CURR`
- `MON_AGENT_HEARTBEAT_HIST`

**API 구현**
- 하트비트 수신 API를 제공한다.
- 서버 시간 차이, Agent 버전, 큐 적재량, Collector 상태를 수신한다.

**데몬 구현**
- Agent 자체 상태, 로컬 큐 건수, 마지막 전송 성공 시각을 전송한다.

**웹 화면 구현**
- 최종 수신 시각, 지연시간, Agent 상태, 버전을 표시한다.

## 4.4 유지보수 및 계획 정지

### MON-SRV-006 유지보수 시간 설정

- 서버별 또는 그룹별 점검 시작·종료 시간을 등록한다.
- 점검 중에는 이벤트 생성을 억제하거나 별도 상태로 표시한다.

**DB 구현**
- `MON_MAINTENANCE`
- `MON_MAINTENANCE_TARGET`

**API 구현**
- 유지보수 일정 등록, 수정, 취소 API를 제공한다.
- 이벤트 판정 시 유지보수 여부를 확인한다.

**데몬 구현**
- 수집은 계속하되 중앙 설정에 따라 원격 명령을 제한할 수 있다.

**웹 화면 구현**
- 달력형 점검 일정, 현재 점검 중 서버 목록을 제공한다.

# 5. 서버 자원 모니터링

## 5.1 CPU 모니터링

### MON-RES-001 CPU 전체 사용률

- 서버 전체 CPU 사용률을 수집한다.
- 기본 수집 주기는 30초 또는 60초로 설정 가능해야 한다.
- 평균, 최대, 최소값을 집계한다.

**DB 구현**
- 지표 코드: `CPU_USAGE_PCT`
- 현재값: `MON_METRIC_CURR`
- 원시이력: `MON_METRIC_HIST`
- 집계: `MON_METRIC_AGG_5M`, `MON_METRIC_AGG_HOUR`, `MON_METRIC_AGG_DAY`

**API 구현**
- 단건이 아닌 Bulk 방식으로 수신한다.
- 값 범위 0~100을 검증한다.
- 서버별 현재값 및 기간 추이 API를 제공한다.

**Windows 데몬 구현**
- `Get-Counter`, WMI/CIM 또는 `psutil`을 이용한다.
- `_Total` CPU 사용률을 수집한다.

**Linux 데몬 구현**
- `/proc/stat`, `psutil`, `mpstat` 중 하나를 이용한다.
- 이전 수집값 대비 변화량으로 사용률을 계산한다.

**웹 화면 구현**
- 현재 CPU 게이지
- 최근 1시간 추이
- 일간 최대·평균
- 임계치 표시선
- CPU 상위 서버 목록

**DB 구현**

**데몬 구현**

# 24. 보안 요구사항

## 24.1 통신 보안

### MON-SEC-001 TLS 적용

- Agent와 API 서버 간 HTTPS를 사용한다.
- Web과 API 서버 간 HTTPS를 사용한다.
- 인증서 만료 및 교체 절차를 정의한다.

### MON-SEC-002 Agent 인증

지원 방식:

1. Agent별 API Key
2. HMAC 서명
3. Client Certificate 기반 mTLS
4. 등록 Token + 장기 인증서 발급

운영 환경에서는 mTLS 또는 Agent별 Key와 HMAC 조합을 권장한다.

### MON-SEC-003 요청 위변조 방지

Agent 요청에 다음 값을 포함한다.

- Agent ID
- Timestamp
- Nonce
- Request Sequence
- Body Hash
- Signature

### MON-SEC-004 재전송 공격 방지

- Timestamp 허용 오차
- Nonce 중복 검사
- Sequence 역행 검사
- 만료된 Token 차단

## 24.2 데이터 보안

## 29.3 PK 및 ID

- 내부 PK는 NUMBER 기반 Identity를 권장한다.

- API 경로에는 추측 가능한 순번 PK보다 외부 식별자 사용을 권장한다.

## 29.4 파티션

파티션 적용 대상:

- `MON_METRIC_HIST`
- `MON_LOG_ENTRY`
- `MON_EVENT`
- `MON_AGENT_HEARTBEAT_HIST`
- `MON_WEB_CHECK_RESULT`
- `MON_BATCH_EXEC`

권장:

- 원시 Metric: 일 또는 월 Range Partition
- 로그: 일 Range Partition
- 이벤트: 월 Range Partition
- 오래된 데이터는 Partition Drop 방식으로 삭제

## 29.5 인덱스

주요 인덱스:

```text
(SERVER_ID, COLLECTED_AT)
(SERVER_ID, METRIC_CODE, COLLECTED_AT)
(EVENT_STATUS, SEVERITY_CODE, OCCURRED_AT)
(BATCH_ID, STARTED_AT)
(LOG_SOURCE_ID, LOGGED_AT)
(AGENT_ID, RECEIVED_AT)
```

주의:

- 이력 테이블에 과도한 인덱스를 생성하지 않는다.
- 조회 패턴을 기준으로 Local Index를 검토한다.
- CLOB 원문 검색은 Oracle Text 적용을 검토한다.

## 29.6 현재 상태 Upsert

- Oracle `MERGE`를 이용해 서버·지표별 최신 상태를 갱신한다.
- 늦게 도착한 과거 데이터가 현재 상태를 덮어쓰지 않도록 `COLLECTED_AT` 비교 조건을 둔다.

## 29.7 보관 정책 예시

| 데이터 | 원시 보관 | 집계 보관 |
|---|---:|---:|
| 30초·60초 Metric | 90일 | 5분 1년, 시간 3년, 일 5년 |
| Agent Heartbeat | 30일 | 일 통계 3년 |
| 로그 원문 | 30~90일 | 오류 통계 3년 |
| 이벤트 | 5년 | 5년 |
| 장애 | 영구 또는 정책 기간 | 영구 |
| 감사 로그 | 5년 이상 | 해당 없음 |
| 명령 이력 | 5년 | 해당 없음 |
| 보고서 | 3~5년 | 해당 없음 |

## 29.8 트랜잭션

- Metric 원시 저장과 현재 상태 갱신은 동일 요청 내에서 처리하되, 대량 적재 성능을 고려한다.
- 알림 전송은 DB 저장 트랜잭션과 분리하고 Queue 기반 비동기로 처리한다.
- 이벤트 생성은 중복 방지를 위해 유일키 또는 Lock 전략을 적용한다.

# 35. 구현 시 주의사항

1. Metric과 로그를 동일한 방식으로 저장하지 않는다.
2. 서버 미수신은 Agent 장애, 서버 종료, 네트워크 장애를 구분할 수 있도록 관련 상태를 함께 본다.
3. 현재 상태 갱신 시 과거 지연 데이터가 최신 상태를 덮어쓰지 않도록 한다.
4. Oracle 이력 테이블은 초기부터 파티션을 적용한다.
5. 로그 원문 장기 보관은 Oracle 용량 증가를 유발하므로 보관기간을 엄격히 설정한다.
6. OS 명령 결과 Parsing에만 의존하지 말고 가능하면 OS API 또는 안정적인 라이브러리를 사용한다.
7. Windows PowerShell 실행 정책과 Linux sudo 권한을 최소화한다.
8. 원격 명령은 임의 Shell 실행 기능으로 만들지 않는다.
9. 임계치의 발생 조건과 복구 조건을 다르게 설정하여 이벤트가 반복적으로 열리고 닫히는 현상을 방지한다.
10. Agent와 중앙 간 데이터는 Batch ID와 Sequence를 이용해 중복 및 누락을 관리한다.
11. 사용자 화면의 서버 상태는 단일 지표가 아니라 Agent, 자원, 프로세스, 서비스, 업무 이벤트를 종합해 산정한다.
12. 서버별 설정과 그룹 공통 설정의 우선순위를 정의한다.
13. 모든 설정 변경은 버전과 감사 로그를 남긴다.
14. 장애 복구 후에도 원인, 조치, 재발 방지 정보를 입력할 수 있게 한다.
15. API 서버 자체와 Oracle DB 자체도 별도 대상 서버로 등록해 자기 모니터링하도록 구성한다.

# 37. 완료 기준

본 시스템은 다음 조건을 충족하면 기본 구축이 완료된 것으로 본다.

1. Windows 및 Linux Agent가 서비스 형태로 자동 실행된다.
2. 중앙 API 장애 중 수집 데이터가 유실되지 않는다.
3. 서버별 CPU, 메모리, 디스크, 네트워크 상태를 조회할 수 있다.
4. 프로세스, 서비스, 포트 상태를 조회할 수 있다.
5. Oracle DB 상태와 Tablespace 사용률을 조회할 수 있다.
6. 배치 및 파일 연계 성공·실패를 조회할 수 있다.
7. 임계치 초과 시 이벤트가 생성되고 복구 시 자동 해제된다.
8. 이벤트에 대한 알림이 발송된다.
9. 장애 접수부터 종료까지 이력을 관리할 수 있다.
10. 사용자 권한에 따라 조회·설정·명령 기능이 제한된다.
11. 모든 주요 변경 및 명령 이력이 감사 로그에 기록된다.
12. Web 대시보드에서 전체 서버 상태를 한눈에 확인할 수 있다.
13. Oracle 파티션과 보관 정책에 따라 이력 데이터가 관리된다.
14. 서버별 Windows/Linux 설정과 Collector 활성화 여부를 관리할 수 있다.
15. API, 데몬, Web의 역할이 분리되어 독립적으로 배포·확장 가능하다.
