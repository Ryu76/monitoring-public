# 프로그램 개발사업 테스트 계획 및 수행 가이드

## 1. 문서 목적

본 문서는 프로그램 개발 완료 이후 시스템의 기능, 성능, 안정성, 보안성 및 운영 적합성을 검증하기 위한 테스트 방법과 수행 절차를 정의한다.

개발자가 구현한 기능이 요구사항에 맞게 동작하는지 확인하는 것뿐 아니라, 실제 운영환경에서 발생할 수 있는 장애, 데이터 오류, 사용자 오조작, 외부 시스템 연동 실패 등에 대한 대응 가능 여부까지 확인하는 것을 목적으로 한다.

---

## 2. 테스트 기본 원칙

테스트는 다음 원칙에 따라 수행한다.

1. 요구사항 명세서 및 화면/기능 설계서를 기준으로 테스트한다.
2. 정상 상황뿐 아니라 오류 및 예외 상황을 반드시 포함한다.
3. 기능 단위 테스트 후 기능 간 연계 테스트를 수행한다.
4. 실제 운영환경과 최대한 유사한 환경에서 통합 테스트를 수행한다.
5. 테스트 결과는 성공/실패 여부와 근거를 기록한다.
6. 오류가 발생한 경우 재현 방법, 원인, 조치내용, 재시험 결과를 관리한다.
7. 운영 반영 전 중요 기능에 대한 회귀 테스트를 수행한다.

---

# 3. 전체 테스트 단계

권장 테스트 진행 순서는 다음과 같다.

```text
개발 완료
   ↓
1. 단위 테스트(Unit Test)
   ↓
2. 기능 테스트(Function Test)
   ↓
3. 통합 테스트(Integration Test)
   ↓
4. 데이터/DB 테스트
   ↓
5. 인터페이스/API 테스트
   ↓
6. 예외/장애 테스트
   ↓
7. 성능/부하 테스트
   ↓
8. 보안 테스트
   ↓
9. 호환성/환경 테스트
   ↓
10. 사용자 인수 테스트(UAT)
   ↓
11. 회귀 테스트(Regression Test)
   ↓
12. 배포 전 최종 점검
   ↓
운영 반영
```

---

# 4. 단위 테스트(Unit Test)

## 4.1 목적

함수, 클래스, 모듈, API Handler, Service, Repository 등 프로그램의 최소 기능 단위가 정상적으로 동작하는지 확인한다.

## 4.2 주요 테스트 내용

- 입력값에 대한 정상 결과 확인
- NULL 또는 빈 값 처리
- 최대/최소값 처리
- 잘못된 데이터 형식 처리
- 조건문 분기 확인
- 반복문 종료조건 확인
- 예외 발생 시 처리 확인
- DB 조회/등록/수정/삭제 로직 확인

## 4.3 예시

```text
기능 : 사용자 조회

정상 입력
USER_ID = USER001
→ 사용자 정보 정상 반환

존재하지 않는 사용자
USER_ID = USER999
→ 데이터 없음 메시지 반환

빈 값
USER_ID = NULL
→ 요청 오류 또는 빈 값 검증 처리
```

---

# 5. 기능 테스트(Function Test)

## 5.1 목적

화면 및 기능이 요구사항에 맞게 구현되었는지 확인한다.

## 5.2 주요 확인 항목

### 로그인/인증

- 정상 로그인
- 비밀번호 오류
- 존재하지 않는 계정
- 비활성 계정
- 권한 없는 사용자 접근
- 세션 만료
- 로그아웃

### 조회 기능

- 전체 조회
- 조건 조회
- 검색 결과 없음
- 대량 데이터 조회
- 정렬
- 페이징

### 등록 기능

- 정상 등록
- 필수값 누락
- 중복 데이터 등록
- 잘못된 값 입력
- 입력 길이 초과

### 수정 기능

- 정상 수정
- 존재하지 않는 데이터 수정
- 동시에 동일 데이터를 수정하는 경우

### 삭제 기능

- 정상 삭제
- 연관 데이터 존재 시 삭제
- 삭제 권한 없는 사용자
- 이미 삭제된 데이터 재삭제

---

# 6. 통합 테스트(Integration Test)

## 6.1 목적

각 기능 및 모듈이 연결된 상태에서 전체 업무 흐름이 정상적으로 처리되는지 확인한다.

## 6.2 테스트 예시

```text
사용자 로그인
    ↓
사용자 정보 조회
    ↓
업무 등록
    ↓
DB 저장
    ↓
처리 담당자 조회
    ↓
알림 발송
    ↓
처리 완료
    ↓
처리 결과 조회
```

각 단계에서 데이터가 정상적으로 전달되는지 확인한다.

## 6.3 주요 확인 항목

- 화면 ↔ API
- API ↔ Business Logic
- Business Logic ↔ DB
- 시스템 ↔ 외부 시스템
- 배치 ↔ DB
- 서버 ↔ 클라이언트
- 프로그램 ↔ 장비

---

# 7. 데이터베이스 테스트

## 7.1 데이터 정합성

다음 항목을 확인한다.

- 등록 데이터 정상 저장 여부
- 수정 데이터 정상 반영 여부
- 삭제 데이터 정상 처리 여부
- 중복 데이터 발생 여부
- NULL 처리 여부
- 기본값 정상 입력 여부
- 날짜 및 시간 저장 형식
- 숫자형 데이터 범위
- 문자 인코딩

## 7.2 트랜잭션 테스트

다음 상황을 확인한다.

```text
INSERT 성공
UPDATE 성공
외부 처리 실패
```

외부 처리 실패 시 전체 작업이 Rollback 되어야 하는지 또는 일부 데이터는 유지되어야 하는지 업무 규칙에 따라 확인한다.

## 7.3 동시성 테스트

동일한 데이터를 여러 사용자가 동시에 수정하는 경우를 확인한다.

예시

```text
사용자 A : 데이터 수정
사용자 B : 동일 데이터 수정
```

확인 항목

- 데이터 덮어쓰기 여부
- Lock 발생 여부
- Deadlock 발생 여부
- 데이터 정합성 유지 여부

# 8. API 테스트

API 기반 시스템인 경우 다음을 확인한다.

## 8.1 HTTP Method

```text
GET
POST
PUT
PATCH
DELETE
```

각 Method가 설계대로 동작하는지 확인한다.

## 8.2 HTTP Status Code

예시

| 상태코드 | 의미 |
|---|---|
| 200 | 정상 |
| 201 | 생성 성공 |
| 400 | 잘못된 요청 |
| 401 | 인증 실패 |
| 403 | 권한 없음 |
| 404 | 데이터 없음 |
| 409 | 데이터 충돌 |
| 500 | 서버 오류 |

## 8.3 API 예외 테스트

- 필수 파라미터 누락
- 잘못된 JSON
- 타입 오류
- 존재하지 않는 ID
- 인증 Token 없음
- 만료된 Token
- 권한 부족
- 요청 크기 초과
- Timeout
- 외부 API 장애

## 8.4 응답 데이터 확인

- Response 구조
- 데이터 타입
- NULL 처리
- 오류 메시지
- 개인정보 노출 여부

---

# 9. 예외 및 장애 테스트

정상 상황만 테스트하면 운영 중 발생하는 문제를 확인하기 어렵기 때문에 장애 상황을 의도적으로 발생시켜 테스트해야 한다.

## 9.1 DB 장애

테스트 예시

```text
DB 종료
DB 연결 차단
DB 세션 강제 종료
DB 응답 지연
```

확인 항목

- 프로그램 비정상 종료 여부
- 사용자 오류 메시지
- DB 재연결 가능 여부
- 로그 기록 여부
- Timeout 처리 여부

## 9.2 네트워크 장애

테스트 예시

```text
Network Disconnect
Packet Loss
지연 발생
DNS 오류
외부 서버 응답 없음
```

확인 항목

- 재시도 여부
- Timeout 적용 여부
- 사용자 화면 Hang 발생 여부
- 오류 처리 여부

## 9.3 서버 장애

- Application Server 종료
- API Server 종료
- 서비스 강제 종료
- 서버 재시작

확인 내용

- 서비스 자동 시작 여부
- 데이터 복구 여부
- 진행 중 작업 상태

## 9.4 외부 시스템 장애

외부 시스템과 연동하는 경우 반드시 테스트한다.

예시

```text
외부 인증 서버 장애
결제 서버 장애
메시지 서버 장애
장비 통신 장애
```

확인 항목

- Timeout
- 재시도
- 대체 처리
- 오류 기록
- 사용자 안내

# 10. 성능 테스트

## 10.1 응답속도 테스트

주요 화면과 API의 응답시간을 측정한다.

예시 기준

```text
일반 조회 : 3초 이내
등록/수정 : 3초 이내
대량 조회 : 5초 이내
API 응답 : 1~3초 이내
```

※ 실제 목표값은 사업 요구사항에 따라 별도로 정의한다.

## 10.2 부하 테스트

동시에 다수 사용자가 시스템을 사용하는 상황을 가정한다.

예시

```text
동시 사용자 10명
동시 사용자 50명
동시 사용자 100명
동시 사용자 500명
```

측정 대상

- CPU
- Memory
- Disk I/O
- Network
- DB Connection
- API Response Time
- Error Rate

## 10.3 스트레스 테스트

시스템의 한계점을 확인한다.

예시

```text
100 User
500 User
1000 User
2000 User
```

사용자 증가에 따른 응답시간과 오류 발생 여부를 확인한다.

# 11. 보안 테스트

## 11.1 인증 테스트

- 인증 없는 API 접근
- 세션 위조
- Token 변조
- 만료 Token 사용
- 로그아웃 Token 재사용

## 11.2 권한 테스트

예시

```text
일반 사용자 → 관리자 API 접근
일반 사용자 → 관리자 화면 접근
일반 사용자 → 다른 사용자 데이터 수정
```

권한이 없는 기능은 반드시 차단되어야 한다.

## 11.3 입력값 검증

다음 공격 또는 비정상 입력을 확인한다.

- SQL Injection
- XSS
- Command Injection
- Path Traversal
- 비정상 JSON
- 특수문자 입력
- 매우 긴 입력값

## 11.4 중요정보 노출 확인

다음 정보가 사용자 화면, API 응답, 로그 등에 노출되지 않는지 확인한다.

- DB Password
- API Key
- Access Token
- 개인식별정보
- 서버 내부 경로
- Stack Trace
- SQL Query 원문

## 11.5 암호화 확인

- HTTPS 적용
- 비밀번호 Hash 저장
- 중요 설정정보 암호화
- Cookie Secure/HttpOnly 설정

# 14. 설치 및 배포 테스트

- 신규 설치


# 15. 로그 테스트

운영환경에서는 로그가 장애 원인을 확인하는 핵심 자료이므로 반드시 점검한다.

## 확인 로그

```text
Application Log
API Log
DB Error Log
System Log
Security Log
Access Log
```

## 확인 항목

- 오류 발생 시간
- 사용자 ID
- 요청 API
- 오류 코드
- 오류 내용
- 처리 결과

단, 비밀번호, 인증 Token, 개인정보 등 중요정보가 로그에 저장되지 않도록 한다.

# 16. 사용자 인수 테스트(UAT)

실제 업무 담당자가 시스템을 사용하여 업무 수행 가능 여부를 확인한다.

개발자가 예상한 사용 흐름과 실제 사용자의 업무 흐름이 다를 수 있기 때문에 운영 전 반드시 수행하는 것이 좋다.

## 주요 확인 항목

- 실제 업무 처리 가능 여부
- 화면 구성 적절성
- 메뉴 접근성
- 업무 프로세스 적합성
- 조회 결과 정확성
- 보고서/통계 정확성
- 불필요한 단계 여부

---

# 17. 회귀 테스트(Regression Test)

프로그램 수정 후 기존 기능에 문제가 발생하지 않았는지 다시 확인한다.

예시

```text
회원 조회 기능 수정

↓

로그인
회원등록
회원수정
회원삭제
회원조회
통계
권한
```

관련 기능 전체를 다시 테스트한다.

특히 공통 모듈, DB Connection, 인증, 공통 API 등을 변경한 경우 전체 시스템에 영향을 줄 수 있으므로 회귀 테스트 범위를 넓게 설정한다.

---

# 20. 결함 관리

테스트 중 발견된 오류는 결함관리 목록으로 관리한다.

## 결함관리 양식

| 항목 | 내용 |
|---|---|
| 결함 ID | BUG-001 |
| 기능 | 로그인 |
| 발생 환경 | 운영체제 / 브라우저 / 버전 |
| 발생 내용 | 로그인 실패 |
| 재현 방법 | ID/PW 입력 후 로그인 |
| 기대 결과 | 로그인 성공 |
| 실제 결과 | 서버 오류 |
| 중요도 | Critical / High / Medium / Low |
| 담당자 | 개발자 |
| 상태 | Open / Fixing / Retest / Closed |

---

# 21. 결함 중요도 기준

## Critical

서비스 사용 자체가 불가능한 오류

예시

- 서버 시작 불가
- 로그인 전체 불가
- 데이터 전체 손실
- DB 연결 불가

## High

주요 기능 사용 불가

예시

- 사용자 등록 불가
- 주요 조회 기능 오류
- 데이터 정합성 오류

## Medium

일부 기능 오류

예시

- 특정 조건 조회 오류
- 일부 화면 오류

## Low

운영 영향이 적은 오류

예시

- UI 위치
- 문구 오류
- 표시 오류

# 25. 권장 테스트 운영 방식

프로그램 개발사업에서는 단순히 "개발 완료 → 사용자 확인 → 운영 적용" 방식으로 진행하기보다 다음 구조를 권장한다.

```text
개발자 테스트
      ↓
QA 기능 테스트
      ↓
통합 테스트
      ↓
성능 / 보안 테스트
      ↓
사용자 UAT
      ↓
결함 수정
      ↓
회귀 테스트
      ↓
운영 배포 테스트
      ↓
운영 반영
```

이를 통해 개발 단계에서 확인하지 못한 기능 오류, 데이터 문제, 운영환경 문제, 사용자 업무 흐름상의 문제를 운영 반영 전에 확인할 수 있다.
